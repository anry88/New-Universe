# `backend/src/features/buildings` directory

Construction queues, demolitions, and building-type reads on player planets.

## Files

- **`building-operation-error.ts`** — `BuildingOperationError` carries deterministic `{ code, details }` pairs for client-safe, localized construction/resource failures.
- **`completion-queue.ts`** — shared BullMQ producer for building completion wake-up jobs. `scheduleBuildingCompletionJob()` reuses one app-lifetime `buildings` Queue/Redis connection, enqueues in fire-and-forget mode after the database transaction commits, logs enqueue failures, and leaves Postgres polling / active-session sync as the fallback completion authority.
- **`count-user-buildings.ts`** — `countUserBuildingsOfType` is the single account-wide counter used when enforcing **`building_types.max_global`** at construction time; it counts both home-system settlements and colony planets.
- **`routes.ts`** — Registers JWT-protected `GET /types`, mutation-rate-limited and JSON-schema-validated `POST /build` (`{ planetId, typeId, slotIndex, selectedResourceId? }`), `POST /upgrade`, **`POST /resource`** (`{ buildingId, selectedResourceId }` for post-build extractor retargeting), `POST /demolish`, `POST /sync/:planetId`, `GET /queue` (includes server-derived **`queueStartedAt`**, per-row **`rushCost`** snapshot, plus **`rushPricing`** meta), and **`POST /rush`** (`{ buildingId }`) under `/buildings`. Build/upgrade responses include the same queue metadata (`planetId`, `buildingTypeId`, `queueStartedAt`, `queueCompletesAt`, `rushCost`) so optimistic clients can replace temporary rows immediately after server confirmation. Structured operation errors are formatted from `Accept-Language` with localized entity labels so raw resource/building ids stay out of response text.
- **`service.ts`** — `BuildingService` owns catalog reads plus transactional **`build`**, **`changeExtractorResource`**, **`upgrade`**, **`demolish`**, **`rushQueuedBuilding`** (spend `users.diamonds`, then **`finalizeBuildingConstruction`** without Telegram notification), **`syncPlanetBuildings`**, **`finalizeBuildingConstruction`**, and planet-aware regen aggregation for passive producers. `getBuildingTypes()` returns rows sorted by canonical seed order (unlock progression). **`build`** first requires an active settlement from `features/colonies/ownership.ts` (capital Command Center or colony record), so merely discovered planets remain read-only until a colonizer arrives. It then passes two building snapshots into eligibility: full rows for per-planet caps, and a dependency snapshot that omits rows still in the initial construction queue (`queueAction === 'build'`) so unfinished builds do not unlock dependents early. Extractor builds and post-build retargeting require a chosen `selectedResourceId`, validate it against local deposits, and reject starts/switches when active/queued extractors already consume all `richness.value` sources for that resource. Retargeting row-locks the building, excludes itself from the target-resource count, updates `selected_resource_id`, then recalculates regen for the old and new resources. Producer finalization recalculates only resources that the completed building can passively produce on that planet; selected extractors produce only their saved resource at the per-resource rate from `@shared/config/resourceExtractionRates`, while processors produce through `production_orders`. Energy-affecting completions/demolitions also call `syncEnergyResourceRow` so battery charge/cap and solar/wind net generation are immediately reflected in `planet_resources.energy`, and `finalizeBuildingConstruction` can invalidate a caller-provided request-scoped energy cache. `syncPlanetBuildings()` also clears stale pending `building_done` notifications for just-synced rows so active players do not get redundant Telegram pushes from worker races. **`build`** and **`upgrade`** persist the queue row first, return full queue metadata for optimistic UI reconciliation, then schedule optional BullMQ delayed jobs through `completion-queue.ts` after commit without request-time Queue/Redis creation or close calls; `tick-buildings` remains the completion path if enqueue fails or BullMQ is disabled. **`upgrade`** revalidates selected extractor deposit limits, uses `@shared/config/buildingUpgradeEconomy` for the **L10** cap, **1.6^currentLevel** cost curve, **1.8^currentLevel × baseTimeSec** timer curve, L6+ extra material kits, and rejects non-Command-Center upgrades whose target level would exceed the local Command Center level. Demolition refunds sum historical build/upgrade spends under the same shared cost curve (50% floor), and `spaceport` demolition is blocked while ships occupy or reserve landing slots on that planet. The seeded Command Center has a basic `iron`/`carbon`/`silicon` `baseCost`, so upgrades are no longer free.
- **`upgrade.ts`** — legacy/alternate upgrade entry point kept aligned with `BuildingService.upgrade` via shared upgrade-economy helpers; HTTP routes call `BuildingService` directly.
- **`buildings.test.ts`**, **`completion-queue.test.ts`**, **`service.test.ts`**, **`upgrade.test.ts`**, **`rush.test.ts`**, **`eligibility.test.ts`** — Vitest coverage over transactional flows, hot-path BullMQ producer behavior, plus pure eligibility ordering rules shared with the frontend.

## Adding limits / prerequisites

1. Extend **`building_types`** through Drizzle (`backend/src/db/schema/buildings.ts`) + migrations + `catalog-rows.ts` seeds (`max_per_planet`, `max_global`, deps JSON).
2. Wire shared eligibility logic (`@shared/types/building-eligibility`) inside **`service.ts`** right after queue-cap checks so the backend rejects duplicates atomically before charging resources.
3. Mirror caps, costs, and extractor rates offline via **`tools/balance-sim/src/catalog.ts`** / **`src/simulate.ts`** when production timings/deps change.
4. Research-gated builds consume **`BUILDING_RESEARCH_GATES`** from **`shared/config/buildingResearchGates.ts`** (re-exported through `backend/src/config/research-unlocks.ts`) so UI previews cannot drift from enforcement order (`research → deps → per-planet → global`). Energy infrastructure keeps `battery` / `solar_plant` available at level 0 and gates advanced `wind_turbine` / `fuel_generator` rows through Energy research.
